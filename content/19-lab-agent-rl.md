## 研究问题

在相同模型、工具接口和调用预算下，环境奖励训练能否提高未见任务成功率？这是可检验的问题。不要一边换模型、一边换提示、一边加训练，再把所有收益归因给 RL。

## 最小设计

| 项目 | 需要预先固定 |
| --- | --- |
| 任务 | 可重置的查询 + 计算任务，按任务族划分训练/测试 |
| 模型 | 适合已有硬件的小模型，固定 revision 与许可证 |
| 基线 | 规则策略、原模型、相同数据 SFT |
| RL 配方 | 一种框架的受支持多轮示例，记录源码 commit |
| 奖励 | 独立程序验证最终结果，显式无效动作与预算处理 |
| 指标 | success@1、成本、超时率、至少 3 个种子 |
| 消融 | 相同 rollout 预算，对比是否使用 RL 或步骤信号 |

## 实施顺序

1. 用官方示例复现一次数据加载和单批训练，不先修改算法。
2. 核对 generated-token mask、行为 logprobs、终止与截断。
3. 小预算试跑，检查 KL、熵、奖励方差和梯度是否异常。
4. 冻结配置，再运行独立测试；保留失败轨迹与总 GPU 小时。
5. 把结果写进实验卡，避免只保存截图和最终分数。

## 资源说明

本库初始化不自动运行 GPU 训练。显存需求取决于模型、优化器、上下文、组大小、并行策略和推理引擎，不能给一个无条件通用的 GB 数字。先按框架文档验证硬件和兼容矩阵，再制定具体预算。

## 停止条件

奖励提高但独立成功率下降、非法工具调用增加、环境版本无法重建、评测集进入奖励调参，都应该暂停并修正。失败结果同样应版本化。
