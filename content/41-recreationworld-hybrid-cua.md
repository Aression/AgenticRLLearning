## 问题与语境

通用计算机使用智能体（CUA）目前沿两条基本不相通的路线发展。一条路线通过图形界面操作真实应用：感知屏幕、发出点击与键盘输入。另一条路线通过代码与命令行工作：编写并运行程序、调用构建/测试/shell 工具、以终端驱动系统。论文指出，这两条路线各自对对方最擅长的事情是盲的：GUI-only 智能体可以观察运行中系统的行为，却很少构建或重配置其背后的软件；terminal-only 智能体可以编写程序并编排工具，却看不到自身动作所产生的界面，因而缺少探索性的视觉反馈来判断运行结果是否符合意图。

这一割裂之所以构成实质问题，在于许多软件密集型任务同时要求两者：理解一个系统需要操作它，而基于该理解采取行动又需要构建或重配置软件。更关键的是，二者不能被当作一次性顺序完成的两个阶段——观察塑造实现，运行实现又重塑下一步该观察什么，信息必须在探索与实现之间反复流动。因此论文主张这是一种真正的融合（hybrid CUA），而非把 GUI 智能体与终端智能体首尾堆叠。

论文对现有做法的失效点定位在测量层面：已有基准多偏重单一交互模式，对智能体在长时程上自主协调这一循环的能力测量不足。换言之，即便模型具备两种模态的能力，也缺少一个能同时要求二者并给出客观奖励的评测载体。

RecreationWorld 的定位正是填补这一测量与训练载体的空缺。它以“复刻”为核心任务：给定一个正在运行的参考应用 $A^{\star}$，智能体需自主探索其行为并构建可运行的候选实现，不规定工作流。参考应用充当预言机，用于生成隐藏行为测试；测试先在参考上验证并冻结，再原样重放于候选，从而给出与实现无关、基于执行的奖励。论文据此提出 RecreationBench（250 个任务，Ubuntu、macOS、Windows、Android、Web 各 50 个），并强调该任务形态天然可验证、可扩展，因而既是评测基准也是训练经验的来源。

## 机制与方法

RecreationWorld 的核心任务形式是「应用复刻」（application recreation）：给定一个正在运行的参考应用 $A^{\star}$，智能体需自主探索其行为并交付一份可运行的候选实现，工作流不作规定。任务由三部分定义：输入为高层任务提示、可交互的参考应用 $A^{\star}$、以及同时含 GUI 控制与软件开发工具的环境；交互阶段智能体可在「操作参考—编写代码—构建并启动候选—视觉与行为核对」之间反复切换，任务只规定目标产物，不规定动作顺序与模态；输出为满足平台构建与启动契约的完整源码 $S$，构建启动后得到可运行候选 $\widehat{A}$。评测只针对可观察行为，不要求复刻参考的架构或源码结构。

奖励信号来自「参考即预言机」的设计：从运行中的参考派生隐藏行为测试，测试先在参考上验证并冻结，再原样重放于候选，从而得到与实现无关、基于执行的奖励。这被作者表述为「验证不对称性」（asymmetry of verification）的一个实例——验证比生成更容易，因而可用客观可执行的信号进行评分与选择。测试分两条互补通道：

- **Prog**：通过平台原生自动化接口（AT-SPI、AXUIElement、UI Automation、UiAutomator）读取精确文本、控件状态、导航、持久化与计算值；桌面与 Android 计通过比例，Web 按特异性加权功能检查。
- **VLM**：在冻结的视觉检查点，将候选截图与参考锚定的自然语言断言配对，由共享判定模型 Qwen3.7-Plus 在温度为零下给出二元结论；桌面与 Android 计断言通过比例，Web 先在页面与视口内聚合再跨页合并。

汇总方式为：平台内对应用做宏平均，平台间等权加权；需要单一汇总值时取两通道均值。评测重放时，每个保留用例固定其 fixture（任务提供的数据或状态，如文档、媒体文件、目录树，属评测输入而非断言或期望答案）、初始状态、交互序列与期望观测；同一设置在参考与每个候选上运行。期望用例缺失、崩溃或未被触达即判失败，候选无法构建或启动得零分。套件冻结 Prog 与 VLM 两份清单，候选无法改变自己的分母。

执行基础设施是实验契约的一部分：每次 rollout 获得版本化、任务隔离的 worker，固定图形运行时、自动化接口与常用构建工具链；worker 在水平扩展的虚拟机池上调度，并在反复的「探索—实现—验证」循环间保留工作区、构建产物、运行进程与图形状态，以维持长时程连续性。预算按轨迹而非短请求分配，复刻任务的单次 rollout 墙钟超时设为 20 小时，使有效交互时程由任务复杂度而非基础设施截断决定。平台原生语义被保留：桌面 worker 暴露交互式操作系统会话与原生截图、输入、无障碍树访问；Android worker 托管固定版本、硬件加速的模拟器；Web worker 本地服务参考并通过 Playwright 驱动捆绑的无头 Chromium。主基准将这些平台动作暴露为 direct-MCP 工具调用。

隔离与完整性是方法的前提条件：模型生成的命令、进程与产物被视为不可信。若不隔离，智能体可能读取本机上的参考源码或构建产物，或从互联网取回上游仓库，使复刻退化为源码复制。因此环境只暴露运行中的界面、可写工作区与必要工具和输入，扣留参考产物、隐藏评测材料与凭据；交接时终止智能体自有进程并冻结候选树，隔离检查失败使该次运行作废而非降低模型得分。

适用前提与已知边界：桌面与 Android 实现源码盲设定（source-blind），但 **Web 无法强制同一边界**——静态站点的客户端实现正是服务器所发送的内容，智能体可检查 HTML、样式、脚本与资源，Web 上受保护的是捕获的 ground truth 与生成的测试套件。此外，作者报告生成的应用比参考更小、更单体化，且交互与计算输出的复现比静态界面结构更差（见 §6.2、§6.3 与 §8 结论，属作者主张）。这些边界意味着该方法最适用于「参考行为可通过结构化自动化接口与冻结视觉检查点被稳定观测」的场景，对依赖远程服务、状态不可在设备内观测或渲染语义难以断言的任务，其可验证性会下降。

## 实验设置

评测在留出集 RecreationBench 上进行：共 250 个任务，Ubuntu、macOS、Windows、Android、Web 各 50 个，覆盖异构 UI 框架、构建系统与无障碍/自动化栈；平台允许时扣留参考实现。每个复刻 rollout 的墙钟预算为 20 小时。评测重放参考验证过的隐藏套件于干净环境中的候选，Prog 与 VLM 分通道报告，平台内宏平均、平台间等权加权，需要单一汇总值时取两通道均值。

训练侧：训练任务取自 GitHub 上高质量开源 GUI 应用，覆盖与 RecreationBench 相同的五个平台族，并与评测集去重。使用 Qwen3.8-Max 通过 RecreationWorld 的 agentic 框架生成复刻轨迹，并以任务特定的行为验证器做拒绝采样筛选高分轨迹；每平台取 7,000 条，构成 35,000 条轨迹的平衡 SFT 混合（按轨迹数平衡，轨迹长度与 token 贡献可能跨平台不同）。在该混合上微调两个模型初始化：Qwen3.7-Plus（完全后训练的起点）与 Qwen-Flash-CPT（内部 Qwen-Flash 检查点经持续预训练后）。

迁移评测使用五个 OOD 基准：三个编码基准 ProgramBench、GameCraft-Bench、Vision2Web，两个计算机使用基准 OSWorld 2.0 与 WeaveBench；均使用 Claude Code scaffold，每个检查点每任务一次试验，报告 0–100 的 graded 分数。

## 证据强度评估

证据分级：B（中等偏强，但结论可迁移性受限）。

理由。正面：评测对象是「可执行行为」而非源码相似度，奖励由参考应用作为预言机生成、先在参考上验证并冻结、再原样重放于候选，属于执行接地（execution-grounded）的客观信号，天然规避了人工偏好标注；测试分 Prog（AT-SPI / AXUIElement / UI Automation / UiAutomator 读取精确文本、控件状态、导航、持久化、计算值）与 VLM（冻结视觉检查点、共享 Qwen3.7-Plus 判定、temperature 0、二元结论）两条互补通道，且套件冻结使候选无法改变自身分母；隔离与完整性有专门设计（§4.5：仅暴露运行界面、可写工作区与必要工具，交接时终止 agent 进程并冻结候选树，隔离检查失败则作废该次运行而非降分），并有 §6.4 的精确行重叠审计（中位 0.014%–0.088%）。这些使「GPT-6 Astra 取得最高总分 58.06%」这一相对排序在给定设置内可信度较高。

主要威胁（按严重度排序）：

1. 构造效度：Prog 与 VLM 的汇总方式（平台宏平均后等权、必要时取两通道均值）是作者自定，摘录未给出通道权重敏感性分析；VLM 通道依赖单一判定模型与二元输出，判定模型自身的偏差未被量化。此外 §6.2 指出候选无需复现参考架构，故「复刻保真度」与「行为等价」之间存在解释空间。

2. 外部效度：训练迁移证据仅覆盖两个模型初始化、五个 OOD 基准，且 §A.5 说明每个 checkpoint 每任务只评一次、使用 Claude Code scaffold 与基准特定预算——单次评测、无重复采样，无法区分真实能力提升与采样噪声；「最高 +17.9 pp」是跨基准取最大值，摘录未给出各基准的绝对分与置信区间。

3. 基线选择与混杂：十模型横评中模型身份、agent scaffold（Codex / Claude Code）、上下文窗口（256k–1M）、最大输出（32k–128k）与推理档位同时变化，§5.1 与 §6.1 均自述这类比较不隔离单一因素，因此 58.06% 对 44.16% 的差距不能归因于模型能力本身。

4. 评测污染与平台不对称：§6.4 的精确行重叠审计只覆盖文本重叠，不覆盖「模型在预训练中见过上游开源仓库」这一记忆性污染；同时 limits 明确指出 Web 无法强制 source-blind（可查看 HTML/JS），而 Web 恰是 GPT-6 Astra 平均分最高（65.05%）的平台，该平台的分数与桌面/Android 的 source-blind 设定不可直接并列。作者主张 C2（唯一多平台全量 Prog 通过）与 C4（静态结构易复现、交互与计算输出难复现）目前均为作者单方分析，无第三方复现，应视为待验证。

## 边界与反例

**会推翻 C1/C2 的观察。** 若在相同 direct-MCP 接口、相同 20 小时/rollout 预算下重跑，GPT-6 Astra 的总分不再领先，或出现第二个模型在多个平台达到全量 Prog 通过，则“唯一性”主张（C2）失效。注意 C1 的 58.06% 与引文中的 “58.1%” 是同一数字的两种写法，但证据表中 GPT-5.6 Sol 的 42.06% 与 Claude Opus 5 的 44.16% 仅来自 §5.1 正文，未见逐平台表，读者不应据此推断平台间排序。

**最可能失效的条件。**
- **Web 平台不可 source-blind**（limits 明确列出）：Web 参考的 HTML/JS/资产可被直接查看，因此 Web 子集测的更接近“读源码后重写”而非“从行为反推规格”。若把 Web 分数单独拆出，其与桌面/Android 的可比性存疑，作者未给出该拆分下的结论。
- **重建产物系统性偏小、偏单体化**（C4、§6.2、§8）：既然候选规模与参考差若干量级，那么“行为保真”可能只在被测试的行为切片上成立；未被断言覆盖的行为（长尾交互、计算输出）无法从分数中读出。
- **交互与计算输出比静态界面更难复现**（C4）：这提示分数对“静态结构类”任务更友好，任务池中此类占比会直接影响模型排名，但证据表未给出该占比。

**作者未验证、读者易误推的方向。**
1. **因果性**：§6.1 与 §3.3 均自陈“descriptive comparisons do not establish that these behaviors cause higher scores”。因此“GUI 交互持续到实现开始之后”“后期 checkpoint 更常检查自身渲染输出”只是相关描述，不能读成提升分数的机制。
2. **训练增益的稳健性**：C3 的 “up to +17.9 pp” 是五个 OOD 基准上的最高值，且 §3.2 明说轨迹“not uniformly monotonic”；把 +17.9 pp 当作典型增益是误读。证据表 ablation 亦仅记录“两训练臂均较首个 checkpoint 提升，轨迹非单调”。
3. **训练数据来源**：§3.1 用 Qwen3.8-Max 生成轨迹，而受训初始化之一是 Qwen3.7-Plus；证据表未提供生成模型与被训模型同源所带来的偏差控制，读者不应把 OOD 增益直接外推到异构模型。
4. **预算可比性**：20 小时墙钟超时是“让任务复杂度决定交互视野”的设计选择，而非与短预算基线对齐的公平比较；跨论文比较分数时该预算不可忽略。

## 与知识库的关系

**新增（此前笔记未覆盖）。**
- 一条**可执行预言机式奖励**的完整实例：参考应用 $A^{\star}$ 生成隐藏测试，先在参考上验证并冻结，再原样重放于候选 $\widehat{A}$，从而得到与实现无关、基于执行的奖励。这为“验证不对称性”（asymmetry of verification）提供了可操作的工程模板，而不只是概念。
- **双通道断言设计**：Prog（AT-SPI / AXUIElement / UI Automation / UiAutomator 读精确文本、控件状态、导航、持久化、计算值）与 VLM（冻结视觉检查点 + 共享 Qwen3.7-Plus 判定器，temperature 0，二元结论）。这是对“结构化可访问性树 + 渲染属性”互补性的具体拆分，可链接至 [[评测通道设计]]、[[可访问性树作为观测接口]]。
- **跨五平台的统一交付契约**（Table 1：源码+构建启动 / Gradle→APK / 固定 React 栈→自包含 index.html），以及“平台宏平均、平台等权”的汇总规则，可链接至 [[跨平台智能体评测]]。

**印证。**
- 印证了 [[长时程智能体的执行反馈闭环]]：单条 rollout 内交替探索—实现—构建—验证—修正，且 20 小时墙钟超时按轨迹而非请求分配。
- 印证了 [[拒绝采样筛选轨迹]] 的有效性：7,000/平台、共 35,000 条 SFT 混合，两臂在五个 OOD 基准上均高于首个 checkpoint。
- 印证了 [[GUI 与终端两条路线的割裂]]：§1 明确指出 GUI-only 看不到自己动作产生的界面、terminal-only 无法判断运行结果是否符合意图。

**张力。**
- 与 [[源码盲设定可作为通用隔离手段]] 存在张力：Web 上无法强制 source-blind，作者只能把保护对象从“实现”改为“捕获的 ground truth 与测试套件”。这说明隔离强度是平台相关的，不能作为跨平台等价假设。
- 与 [[重建保真度可用行为分数充分刻画]] 存在张力：C4 显示候选比参考更小、更单体化，交互与计算输出复现更差，说明行为分数并未覆盖实现规模与结构维度。
- 与 [[训练增益可跨环境迁移]] 部分张力：增益为“up to +17.9 pp”且非单调，属作者主张（C3），尚无可复现的独立验证。

## 复现与验证计划

目标：在自有算力上以最小代价检验「复刻任务可作为可验证的混合 CUA 训练/评测基座」这一主张，而非复现全部 250 任务。

环境与任务。按 §2.3 与表 8 搭建：每个 rollout 使用任务隔离 worker，固定图形运行时、自动化接口与构建工具链；桌面暴露原生截图/输入/可访问性树，Android 用固定硬件加速模拟器，Web 本地服务参考并用 Playwright 驱动 headless Chromium。控制侧固定版本：qwen-cua-driver 0.7.3、mobile-mcp 0.1.5、Playwright MCP 0.0.79。参考产物、隐藏测试与凭据必须对智能体不可见（§4.5）；隔离检查失败应判该 run 无效而非扣分。

数据。从 RecreationBench 中按平台各取少量任务（Ubuntu/macOS/Windows/Android/Web），优先选交付契约明确者：桌面为 source + build/launch，Android 为 Gradle→APK，Web 为固定 React 栈→自包含 index.html（表 1）。训练侧若做迁移验证，按 §3.1 用拒绝采样筛高分轨迹，注意其配比为每平台 7,000 条、共 35,000 条。

基线与预算。基线取同一 scaffold 下的首个 checkpoint（§3.2 的做法），单次 rollout 墙钟超时 20 小时（§2.3、表 7）。评测按 §4.4：Prog 与 VLM 分通道报告，平台内先宏平均应用、平台间等权；单通道汇总时取两通道均值。判据：候选无法构建或启动记 0；冻结用例缺失、崩溃或未到达即失败。

预期失败模式。Web 无法强制 source-blind，智能体可读 HTML/JS；重建应用比参考更小、更单体化；交互与计算输出比静态界面更难复现（§6.2、§6.3）。此外 VLM 判定依赖共享 Qwen3.7-Plus judge（temperature 0），judge 传输或解析失败应视为无效测量并重跑，而非模型失败。注意 §6.4 的污染审计：精确行重叠中位数在 0.014%–0.088% 之间，最大值可达 3.188%（macOS），需在自建任务上做同类审计。

## 术语与记号

| 术语 | 含义 |
| --- | --- |
| hybrid CUA | 混合计算机使用智能体：在单一长时程过程中交替使用界面操作与代码/命令行工具，自主决定何时探索、实现与验证 |
| application recreation | 应用复刻：从可执行参考出发构建可运行应用，仅评估可观察行为而非源码结构 |
| RecreationBench | 论文提出的留出评测集，共 250 个任务，Ubuntu、macOS、Windows、Android、Web 各 50 个 |
| RecreationWorld | 围绕复刻构建的框架，标准化参考执行、候选交付与实验日志，同时保留各平台原生交互语义 |
| Prog | 程序化断言通道，通过 AT-SPI、AXUIElement、UI Automation 或 UiAutomator 读取精确文本、控件状态、导航、持久化与计算值 |
| VLM | 视觉断言通道，在冻结视觉检查点将候选截图与参考锚定的自然语言断言配对，由共享判定模型给出二元结论 |
| fixture | 评测输入：重放前安装的任务提供数据或状态，如文档、媒体文件或目录树，而非断言或期望答案 |
| source-blind setting | 源码盲设定：桌面与 Android 上智能体只能观察可执行界面，实现产物被隐藏 |
| rejection sampling | 拒绝采样：用任务特定的行为验证器筛选高分轨迹用于训练 |
| asymmetry of verification | 验证不对称性：验证比生成更容易，因而可用客观可执行的信号评分与选择 |

符号：$A^{\star}$ 为正在运行的参考应用；$S$ 为智能体提交的完整源码；$\widehat{A}$ 为由 $S$ 构建并启动得到的可运行候选应用。任务由三部分定义：输入（高层提示、可交互的 $A^{\star}$、含 GUI 控制与开发工具的环境）、交互（在操作参考、写码、构建启动、视觉与行为检查之间反复切换，不规定顺序与模态）、输出（满足平台构建与启动契约的 $S$）。评测在干净环境中把参考上验证并冻结的隐藏套件原样重放于 $\widehat{A}$，分别计算 Prog 与 VLM 分数，平台内宏平均应用分数、平台间等权加权，必要时取两通道均值作为汇总。注意 Web 的 Prog 按特异性加权，行为与内容权重高于浅层启动或存在性检查。

## 自测

以下问题用于检验你是否真正读懂了 RecreationWorld 的评测契约与证据强度。答案折叠在 `<details>` 中，建议先自行作答。

**Q1（基础）** RecreationBench 的任务规模与平台分布是什么？GPT-6 Astra 的总分与 Prog 全量通过覆盖率分别是多少？

<details><summary>答案</summary>
RecreationBench 共 250 个任务，Ubuntu、macOS、Windows、Android、Web 各 50 个（§1、§4.2）。GPT-6 Astra 取得最高总分 58.06%（§5.1 表；§1 正文写作 58.1%），是唯一在多个平台有全量 Prog 通过的模型，覆盖率为 17.6% 和 2.8%（§5.1）。注意 2.8% 对应的是「100% Prog 覆盖」的任务占比，而非平均分。
</details>

**Q2（基础）** 为什么说 recreation 的奖励是「与实现无关」的？Prog 与 VLM 两条通道各自读什么？

<details><summary>答案</summary>
参考应用充当预言机：隐藏行为测试先在参考上验证并冻结，再原样重放于候选，因此评分只看可观察行为，不约束候选的语言、框架或架构（§2.1、§4.4）。Prog 通过平台原生自动化接口（AT-SPI、AXUIElement、UI Automation、UiAutomator）读取精确文本、控件状态、导航、持久化与计算值；VLM 在冻结视觉检查点，由共享的 Qwen3.7-Plus 判定模型在 temperature zero 下对「候选截图 + 参考锚定的自然语言断言」给出二元结论（§4.4）。
</details>

**Q3（跨小节推理）** 论文声称训练迁移到五个 OOD 基准、增益最高 17.9 pp。结合 §3.2 与 §3.3，这个结论的边界在哪里？为什么 §3.3 的行为变化不能用来解释增益？

<details><summary>答案</summary>
边界有三点：(1) 两条 checkpoint sweep 都高于各自首个评估检查点，但轨迹并非单调（§3.2、证据表 ablations），所以「提升」是相对首个检查点而非单调收敛；(2) 五个基准统一使用 Claude Code scaffold、每任务一 trial，任务数、预算与配置差异见附录 A.5，因此跨基准的绝对分数不可直接横向比较；(3) §3.3 明确说明这些行为指标是描述性的，且三组指标使用不同 estimand（ProgramBench 按 Bash 调用计的验证率、GameCraft-Bench 与 Vision2Web 的每任务读图比例、OSWorld 2.0 与 WeaveBench 的池化 GUI 调用比例），并非同一动作总体的比例，因此不能据此推断行为变化导致了分数提升。
</details>

**Q4（跨小节推理）** 论文把 recreation 称为「天然可验证」的基座，但 §4.1 与 §4.5 又承认 Web 无法强制 source-blind。这两点是否矛盾？对使用该基准的人意味着什么？

<details><summary>答案</summary>
不矛盾，但构成平台间的不对称。桌面与 Android 实现 source-blind：智能体只观察可执行界面，实现产物被隐藏；Web 无法做到，因为静态站点的客户端实现正是服务器发送的内容，智能体可以查看 HTML、样式、脚本与资源（§4.1）。Web 上受保护的是捕获的 ground truth 与生成的测试套件，且要求交付页面在评测时不加载参考。§4.5 的隔离机制（只暴露运行界面、可写工作区与必要工具，扣留参考产物、隐藏评测材料与凭据；交接时终止智能体进程并冻结候选树，隔离检查失败则作废该次运行）是缓解手段而非证明。实践含义：Web 子集的分数更易受「读源码」策略影响，跨平台宏平均时需注意这一差异；论文也把 Web 参考视为构建快照，故 §6.2 的源码规模对比只覆盖三个桌面平台与 Android。
</details>

**Q5（跨小节推理）** 若你要把 RecreationWorld 用作自己场景的训练数据来源，§3.1 的 SFT mixture 与 §6.2/§6.3 的失败模式分析分别提示了哪些风险？

<details><summary>答案</summary>
数据侧：SFT mixture 为 35,000 条轨迹、每平台 7,000 条，用 Qwen3.8-Max 生成并经任务特定行为验证器做拒绝采样筛选（§3.1）。平衡是按轨迹条数而非 token 数，轨迹长度与 token 贡献可能跨平台不同，因此「均衡」不等于等量监督信号；且训练任务与评测集做了去重，迁移结论来自 OOD 基准而非同分布。能力侧：智能体更可靠地复现静态界面结构，交互与计算输出的复现更差，生成应用比参考更小、更单体化（§6.2、§6.3、§8）。这意味着直接迁移到「重交互、重计算」的目标场景时，recreation 监督可能覆盖不足；同时 §6.1 提醒模型身份、harness 与 runtime 是共同变化的，轨迹层面的比较不能隔离单一行为的因果效应。
</details>
